# სამშენებლო კონტრაქტორების სამუშაო სისტემა

განხორციელების თარიღი: 2026-11-04. ცვლილებები ეფუძნება არსებულ Next.js / Prisma / SQLite აპლიკაციას. ამ დავალებაში commit, push და deployment არ შესრულებულა.

## მოქმედი სამუშაო პროცესები

1. **მოთხოვნა → დათვალიერება/შეთავაზება → შეთანხმება → ობიექტი.** შენარჩუნებულია მოთხოვნები, დამკვეთები, კონტაქტები, შენიშვნები და pipeline. ახალ კომპანიას სამშენებლო ეტაპები ექმნება არჩეულ ენაზე. მოგებული შეკვეთიდან ობიექტი იქმნება ერთხელ: გადმოდის დამკვეთი, დასახელება, მისამართი, მენეჯერი, ვალუტა და შეკვეთის კავშირი. ძველი pipeline-ის სახელები არ გადაიწერება.
2. **ობიექტი → ხარჯთაღრიცხვა → ბიუჯეტი.** ობიექტს აქვს ნომერი, მისამართი, სამუშაოს ტიპი, აღწერა, მენეჯერი, უბნის პასუხისმგებელი, თარიღები, ხელშეკრულების მითითება, სტატუსი და ცალკე სამუშაო პროცესის ეტაპი (დათვალიერება → ხარჯთაღრიცხვა → შეთავაზება → ხელშეკრულება → შესრულება → აქტი → გადახდა → ჩაბარება). ხარჯთაღრიცხვა მოიცავს სამუშაოს რაოდენობასა და ერთეულს, მასალის, შრომის, ქვეკონტრაქტორის, ტექნიკისა და სხვა ხარჯს, დამატებით ხარჯს, ფასნამატს და მომხმარებლის მიერ არჩეულ დღგ-ს. მონახაზს შეიძლება დაემატოს/წაეშალოს სტრიქონები და შეეცვალოს განაკვეთები; დამტკიცებული ვერსია უცვლელია. რევიზია ქმნის ასლს და დამტკიცებამდე არ ცვლის აქტიურ ბიუჯეტს. ძველი ვერსიები ინახება.
3. **დაგეგმილი სამუშაო → დღიური შესრულება → პრობლემის გამოსწორება.** სამუშაო უკავშირდება ობიექტს, დამკვეთს, პასუხისმგებელს, რაოდენობას, ერთეულს და ვადას. სამუშაოები შეიძლება დაჯგუფდეს დასახელებული ეტაპებით; ჩანს ეტაპის საშუალო პროგრესი. ანგარიშები აღრიცხავს ზუსტ შესრულებულ მოცულობას, პრობლემას/შეფერხებას ან დეფექტს. დაგეგმილ რაოდენობაზე მეტი შესრულება იბლოკება. მოცულობის სრულად შესრულება ავტომატურად ასრულებს დავალებას; ზოგადი task-board-ის ღილაკით მოცულობის ჩანაცვლება აკრძალულია. ანგარიშს შეიძლება დაერთოს კერძო ფოტო/დოკუმენტი.
4. **მასალის მოთხოვნა → მომწოდებლების შეთავაზებები → შეკვეთა → მიღება → მარაგი.** მოთხოვნაზე შესაძლებელია რამდენიმე შეთავაზება, მაგრამ ერთი შესყიდვის შეკვეთა. ნაწილობრივი მიღება ზუსტ რაოდენობასა და კუმულაციურად დამრგვალებულ ხარჯს აფიქსირებს. შეკვეთაზე მეტის მიღება და უარყოფითი მარაგი იბლოკება. ხელმისაწვდომია ხარჯვა, ადრე გახარჯულის მარაგში დაბრუნება და სხვა ობიექტზე გადატანა. გადატანისას წყაროს ხარჯი მცირდება და მიმღების იზრდება იმავე საშუალო შეწონილი ღირებულებით.
5. **ქვეკონტრაქტორის შეთანხმება → შესრულებული მოცულობის დადასტურება → გადახდა.** ინახება პარტნიორი, სპეციალიზაცია და კონტაქტები, სამუშაო, რაოდენობა, ფასი და დადასტურებული შესრულება. დადასტურება ავტომატურად ასახავს ხარჯს; ზედმეტი მოცულობა იბლოკება. გასული თანხა შეიძლება მიებას კონკრეტულ შეთანხმებას და გამოჩნდეს მის გადახდებში.
6. **შესრულებული სამუშაოების აქტი → ხელით აღრიცხული დადასტურება → ინვოისი → გადახდა.** აქტს აქვს მრავალი სტრიქონი ზუსტი ათწილადი რაოდენობებითა და ფასებით. უფლებამოსილი მომხმარებელი ხელით აფიქსირებს დამკვეთის დადასტურებას; შემდეგ იქმნება აქტთან და ობიექტთან დაკავშირებული ერთი draft ინვოისი. ძველ ინვოისის მოდელში ინახება აქტის ერთი შემაჯამებელი სტრიქონი; დეტალური მოცულობები რჩება აქტში. აღირიცხება ავანსი, ეტაპობრივი, საბოლოო ან სხვა შემოსვლა/გასვლა.
7. **კონტროლი → ჩაბარება.** მთავარი პანელი აჩვენებს ობიექტებსა და პროგრესს, ვადაგადაცილებულ სამუშაოებს, ბიუჯეტგადაჭარბებას, დასამტკიცებელ მოთხოვნებსა და აქტებს, მისაღებ/გადასახდელ ნაშთებს. კალენდარში ჩანს სამუშაოების ვადები, შეთავაზებების თარიღები და ობიექტების ჩაბარება. დასრულების/ჩაბარების სტატუსს მენეჯერი ცვლის ობიექტიდან.

## გამოთვლის წესები

- ფული ინახება მთელ minor-unit-ებში; ერთი ჩანაწერის/ხარჯთაღრიცხვის ზედა ზღვარია 2,147,483,647 minor-unit.
- რაოდენობა ინახება ათწილადის სტრიქონად, მაქსიმუმ სამი ათწილადით. გამოთვლები სრულდება Decimal.js-ით; თანხები მრგვალდება HALF_UP წესით minor-unit-მდე.
- ხარჯთაღრიცხვაში კატეგორიის თანხა = სტრიქონებზე ცალ-ცალკე დამრგვალებული რაოდენობა × ერთეულის ხარჯი. დამატებითი ხარჯი შედის „სხვა“-ში. ფასნამატი ემატება ხარჯს, შემდეგ დღგ ითვლება მიღებულ net თანხაზე.
- შესყიდვის/ქვეკონტრაქტორის ნაწილობრივი შესრულების ხარჯი = ახალი კუმულაციური მოცულობის დამრგვალებული ფასი − წინა კუმულაციური ფასი. ნაწილები სრულ ჯამს ემთხვევა.
- ბიუჯეტის გეგმა = ბოლო დამტკიცებული ხარჯთაღრიცხვის ხარჯი + დამტკიცებული დამატებითი სამუშაოების გეგმური ხარჯი. ცვლილებები „სხვა“ გეგმურ კატეგორიაშია. დაუმტკიცებელი ვერსია/ცვლილება გეგმას არ ცვლის.
- გადახრა = რეალური ხარჯი − გეგმა. მოსალოდნელი მოგება = შეთანხმებული შემოსავალი დღგ-ს გარეშე − გეგმურ და რეალურ ხარჯს შორის უდიდესი.
- მისაღები ნაშთი = დამტკიცებული ხელშეკრულების თანხა ცვლილებებითა და დღგ-ით − ხელით აღრიცხული შემოსვლა. დადასტურებული აქტების ნაშთი ცალკე ჩანს. დამტკიცებული ხარჯთაღრიცხვის გარეშე სახელშეკრულებო ნაშთი არ გამოითვლება.
- გადასახდელი საოპერაციო ნაშთი = დარიცხული ხარჯი დღგ-ს გარეშე − აღრიცხული გასვლა. ეს ხარჯისა და ფულის მოძრაობის შედარებაა და არა მიმწოდებლების ბუღალტრული კრედიტორული უწყისი. უარყოფითი მნიშვნელობა ავანსს/ზედმეტ გადახდას აღნიშნავს.
- ვალუტები ცალ-ცალკე რჩება; გაცვლითი კურსის კონვერტაცია არ ხდება. მარაგის გადატანა დაშვებულია მხოლოდ ერთნაირი ვალუტის ობიექტებს შორის.
- მოცულობითი სამუშაოს თარიღით მითითებული ვადა სრულდება კომპანიის დროის სარტყლის დღის ბოლოს; იმ დღის დასაწყისში ვადაგადაცილებულად არ ითვლება.
- ობიექტის პროგრესი არის სამუშაოების შესრულების პროცენტების თანაბარი წონით საშუალო; ფინანსურ ღირებულებას არ ზომავს.
- ახალ კომპანიას/ახალ დამკვეთს დღგ-ს გადამხდელობა ავტომატურად არ მიენიჭება. ახალი სამშენებლო დოკუმენტის დღგ საწყისად 0%-ია. ძველი საგადასახადო ჩანაწერები არ იცვლება.

## წვდომა, აუდიტი და მონაცემები

- ობიექტის ყველა ოპერაცია ამოწმებს აქტიურ კომპანიას და ობიექტზე წვდომას სერვერზე. მენეჯერი/ადმინისტრატორი ხედავს კომპანიის ობიექტებს; თანამშრომელი — სადაც არის მენეჯერი, უბნის პასუხისმგებელი ან მინიჭებული სამუშაოს შემსრულებელი.
- `construction.manage` და `construction.finance` ცალკე შესაძლებლობებია. ამ ეტაპზე ორივე აქვთ ADMIN/MANAGER როლებს. თანამშრომლის ობიექტზე წვდომა არ აძლევს მას ხარჯთაღრიცხვას, ხარჯებს, შესყიდვის ფასებს, აქტებს, გადახდებს ან ფინანსურ დოკუმენტებს. ცალკე ფინანსური როლის პერსონალიზაციის ეკრანი არ დამატებულა.
- განმეორებითი შეკვეთა/მიღება, შესრულების დადასტურება, აქტი, აქტის ინვოისი და გადახდა არ ქმნის განმეორებით შედეგს იმავე ოპერაციის გასაღებით. წინააღმდეგობრივი გადახდა/აქტის payload იბლოკება. ledger-ის შემოწმებები და ჩანაწერები ტრანზაქციაში სრულდება.
- სამშენებლო ცვლილებები იწერება აუდიტში. JSON v2 ექსპორტი რჩება მხოლოდ ადმინისტრატორის ბრაუზერის ჩამოტვირთვად; დამატებულია ახალი მოდულები და კავშირები. ფაილების შიგთავსი/საცავის გზა, შიდა ოპერაციის გასაღებები, პაროლები და ტოკენები არ გაიცემა. CSV კვლავ მხოლოდ დამკვეთებს შეიცავს.
- ექსპორტი არის გვერდებად წაკითხული ცოცხალი მონაცემები და არა ტრანზაქციულად თანმიმდევრული backup. დეტალები: `WORKSPACE_EXPORT_SPEC.md`.

## მოცილებული ინტერფეისი და კოდი

- ამოღებულია `/feed`, ზოგადი ჩატი, `/hr`, შვებულებები და სამუშაო საათის ღილაკები, მათი server actions და ნავიგაციის ბმულები.
- კალენდარს აღარ აქვს შვებულებების მოთხოვნა/ჩვენება. ძველი `POST_FEED` მოქმედების შესრულება ამოღებულია; მიგრაცია უცნობ/მოცილებულ ავტომატიზაციებს თიშავს მათი ჩანაწერების წაშლის გარეშე. ახალი ავტომატიზაცია მხოლოდ `CREATE_TASK`-ს ქმნის.
- განახლებულია საჯარო გვერდი, ნავიგაცია, ახალი კომპანიის pipeline, მასალების კატალოგის ტექსტები და მომავალი დემო მაგალითები. აღარ არის ყალბი live სტატისტიკა ან გამოუგზავნელი RS.ge დოკუმენტის გაგზავნილად წარმოჩენა ახალ seed-ში.
- ისტორიული HR/feed/chat ცხრილები და არსებული მონაცემები რჩება ბაზაში. ძველი მიგრაციების ისტორია შენარჩუნებულია. მანამდე არსებული დემო ჩანაწერები არ გადაეწერა.

## მიგრაცია და გაშვება

საჭიროა `20261104100000_contractor_workspace` მიგრაცია. ის ამატებს სამშენებლო ცხრილებს და არსებულ Task/Invoice ცხრილებს ახალ nullable კავშირებს, ძველი სვეტების კოპირებით. არსებული ბაზა ამ დავალებაში არ მიგრირებულა; მიგრაცია შემოწმდა ცალკე ტესტის ბაზებზე. database reset არ შესრულებულა.

1. შეინახეთ არსებული SQLite ბაზის backup და მიმდინარე ფაილური საცავი.
2. შესაბამის გარემოში გამართეთ `DATABASE_URL`; საიდუმლო მნიშვნელობები არ დაბეჭდოთ.
3. გაუშვით `npm run db:deploy`, შემდეგ `npm run db:generate` და `npm run build`.
4. გაუშვით აპლიკაცია. `npm run db:seed` ამზადებს ერთ ცარიელ სივრცესა და სამ ანგარიშს (ადმინისტრატორი, მენეჯერი, მომხმარებელი). Alpha/Beta სივრცეებისა და სამშენებლო მაგალითების გენერაცია ამოღებულია. მათი ძველი მონაცემების წაშლა ცალკე, პირდაპირი ბრძანებით სრულდება; იხილეთ README.

ლოკალური მიმოხილვისთვის შეიქმნა ცალკე, Git-ში უგულებელყოფილი `prisma/contractor-preview.db`. ბრაუზერის QA მოქმედებები მხოლოდ ამ სინთეზურ ბაზაში შესრულდა. სამუშაო და tracked demo ბაზები არ შეცვლილა. დროებითი schema-ს ასლი წაიშალა.

## ფაილები და ჰოსტინგის შეზღუდვები

- ლოკალური ატვირთვა/ავტორიზებული ჩამოტვირთვა მუშაობს `storage/construction` კერძო დირექტორიიდან. დაუშვებელია მისი საჯაროდ გამოქვეყნება; საჭიროა მუდმივი დისკი და backup. `storage/` გამორიცხულია Git-იდან.
- დაშვებულია JPEG/PNG/WebP/PDF, მაქს. 8 მბ; მოწმდება ფაილის საწყისი ბაიტები. HTML/SVG არ მიიღება. PDF ჩამოიტვირთება attachment-ად; სურათებს აქვთ შესაბამისი MIME, `nosniff`, კერძო cache და sandbox CSP.
- Vercel-ზე ატვირთვა შეგნებულად არ მუშაობს მუდმივი საცავის გამართვამდე და აჩვენებს შესაბამის შეცდომას. მიმდინარე `/tmp` SQLite დემო არ უზრუნველყოფს მუდმივ სამუშაო მონაცემებს ან ფაილებს. რეალური ჰოსტინგისთვის საჭიროა მუდმივი მონაცემთა ბაზა და ფაილების საცავი.
- არსებული მიგრაციები SQLite SQL-ს შეიცავს. PostgreSQL-ზე გადასვლისთვის მხოლოდ provider-ის შეცვლა საკმარისი არ არის: საჭიროა ცალკე სქემის/მიგრაციის გეგმა და მონაცემების გადატანის შემოწმება.
- თანხის აღრიცხვა არ არის საბანკო გადარიცხვა/დადასტურება; დამკვეთის დადასტურება არ არის ელექტრონული ხელმოწერა. ხარჯთაღრიცხვისა და აქტის PDF ინახება ბრაუზერის Print / Save PDF ფუნქციით.
- მიღებული მასალის ან დადასტურებული ქვეკონტრაქტორის ხარჯს ხელით მეორედ ნუ ჩაწერთ. ავტომატური საბანკო შეჯერება, ბუღალტრული კრედიტორული უწყისი და მიმწოდებელთან დაბრუნების ცალკე პროცესი არ დამატებულა; მასალის „დაბრუნება“ არის გახარჯულიდან ობიექტის მარაგში დაბრუნება.

## შემოწმება

- `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`.
- არსებული `prisma/dev.db` და `prisma/demo-seed.db` ბაზების მეხსიერებაში შექმნილ ასლებზე სრული ახალი მიგრაცია წარმატებით შესრულდა. ყველა ძველი ცხრილის ჩანაწერების რაოდენობა და Task/Invoice-ის ყველა თავდაპირველი ველი შენარჩუნდა; `foreign_key_check` სუფთაა. ორიგინალები გაიხსნა მხოლოდ წაკითხვის რეჟიმში.
- 66 ტესტი, მათ შორის 12 ახალი სამშენებლო ინტეგრაციის სცენარი: მიგრაციისას ძველი ჩანაწერების შენარჩუნება, კომპანიებს შორის იზოლაცია, ობიექტისა და ფინანსების განსხვავებული წვდომა, ხუთივე გეგმური კატეგორია, ზუსტი ათწილადები/დამრგვალება, ვერსიის უცვლელობა, განმეორებითი შესყიდვები/მიღება/გადატანა/ქვეკონტრაქტორის შესრულება/აქტი/ინვოისი/გადახდა, ზედმეტი მოცულობა, ფინანსური დოკუმენტების დაცვა და ექსპორტის ველების გამორიცხვა.
- ბრაუზერი: ქართული და ინგლისური ეკრანები, ღამის/დღის თემა, 390px ტელეფონის განლაგება, ხარჯთაღრიცხვის რევიზიის რეალური შენახვა, დღიური პრობლემის დამატება, 1.125 რაოდენობით/18.5% დღგ-ით აქტის შექმნა (2.94 ჯამი), ხელით დადასტურება და ინვოისის მიბმა, სინთეზური PNG-ის ატვირთვა, თანამშრომლის ფინანსების გარეშე ხედვა.
- შემოწმების ეკრანები და სატესტო ფაილი ინახება `output/contractor-qa/`-ში. ეს სინთეზური მონაცემების QA არტეფაქტებია და არა რეალური კომპანიის ექსპორტი.
